# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Snap Bounty** — a **server-side-only** C#/Harmony mod for *7 Days to Die* **V2.6**. Each player
gets 1–3 rerollable bounties (`/bounty`, `/skip`); completing one spawns a physical loot bag with
2–5 random tiered items. See `README.md` for the user-facing feature list and the full bounty
catalog.

## Build / package / release

The mod compiles against the game's managed DLLs (`Assembly-CSharp.dll`, `UnityEngine*`,
`0Harmony.dll`, `LogLibrary.dll`). `src/SnapBounty.csproj` auto-detects them from a local install
or a CI-installed Dedicated Server via `-p:GameRoot=...` (see the `GameRoot`/`ManagedDir`/
`HarmonyPath` conditions in the csproj). Target framework is **net48**; no Mono needed (uses
`Microsoft.NETFramework.ReferenceAssemblies`).

```bash
dotnet build src/SnapBounty.csproj -c Release          # -> bin/Release/SnapBounty.dll
./build.sh                                              # build + package -> dist/SnapBounty/
GAME_ROOT="/path/to/7 Days To Die Dedicated Server" ./build.sh
DEPLOY_DIR="/path/to/7 Days To Die/Mods" ./build.sh    # also copy into a server's Mods/
```

- **No test suite exists.** Verification is in-game on a dedicated server (the dev machine can't
  launch the game), so changes that touch game APIs must be reasoned about, not unit-tested.
- **CI** (`.github/workflows/ci.yml`, on PRs): installs the Dedicated Server (SteamCMD app 294420,
  cached) for build DLLs, then compiles.
- **Release** (`.github/workflows/release.yml`, manual): builds + **semantic-release**. This repo
  uses **Conventional Commits** — `feat:` → minor bump, `fix:` → patch, `chore:`/`refactor:`/`docs:`
  → no release. Release notes/zip/`ModInfo.xml` version are generated by `scripts/*.sh`.

## Architecture: the C# → XML reward bridge

The mod is split between **C# logic** and **reused vanilla-style XML assets**, connected at one point:

1. **C# tracks progress** and, on completion, calls
   `GameEventManager.Current.HandleAction("snapBountyReward_tX", player, …)`.
2. That fires an `<action_sequence>` in `SnapBounty/Config/gameevents.xml` whose `SpawnContainer`
   action spawns the loot-bag entity defined in `SnapBounty/Config/entityclasses.xml`
   (extends `twitch_crate_template`, `Prefab="Backpack"`), filled from a loot group in
   `SnapBounty/Config/loot.xml` (`count="2,5"` → random 2–5 items).

So loot content/quantity is tuned in `Config/loot.xml` (no rebuild), while bounty behavior is C#.

### Server-side-only constraint (critical)

This mod runs **only on the server**; clients install nothing. Therefore **only
server-authoritative events can be hooked** — client-side code (hand-crafting UI, vanilla challenge
tracking) does NOT execute on a dedicated server. The verified hooks in use:

- Kills: `ModEvents.EntityKilled`
- Mine/build blocks: Harmony postfix on `GameManager.SetBlocksRPC` (`BlockChangeInfo` →
  `changedByEntityId`, `blockValue.isair`, `blockValue.Block.GetBlockName()`)
- Crafting: Harmony postfix on `TileEntityWorkstation.AddCraftComplete` — **workstations only**
- Biomes: throttled polling of `EntityPlayer.biomeStandingOn` via `ModEvents.GameUpdate`

`HarmonyPatches.cs` holds the patches; `ModApi.cs` (`IModApi.InitMod`) wires events + `PatchAll`.

### Source map

- `ModApi.cs` — entry point: load config, register ModEvents + Harmony, parse `/bounty` & `/skip`.
- `BountyManager.cs` — per-player state, assign/refill, the generic `Award(...)` core, `/skip`
  cooldown, reward trigger, biome polling. Player key = `ClientInfo.PlatformId.CombinedString`.
- `Bounties.cs` — `BountyDef` + `BountyCatalog` (built-in defaults; `BuildDefaults()` is the source
  of truth, `All` is the effective catalog after config overrides).
- `Config.cs` — parses `snapbounty.xml`.
- `Persistence.cs` — text file at `<save>/SnapBounty/bounties.txt`.

### Config file gotcha

`SnapBounty/snapbounty.xml` (settings + per-bounty count/tier/enabled) lives in the **mod root**,
read by C# via `Mod.Path` — **not** in `Config/`, because the game's XPatch loader would try to
apply any `Config/*.xml` against a same-named vanilla config. When adding a bounty, add it in
`Bounties.cs` **and** as a `<bounty>` line in `snapbounty.xml` (the `<bounties>` list is
authoritative: only listed+enabled bounties are used; ids must match).

## No hallucinated game identifiers

Entity class names, item names, block names, recipe names, biome names, and C# API signatures
**must be verified against the real game files**, never guessed. They live at:
`~/Library/Application Support/Steam/steamapps/common/7 Days To Die/7DaysToDie.app/Data/Config/`
(XML) and `.../Contents/Resources/Data/Managed/` (DLLs, e.g. `Assembly-CSharp.dll`).

To inspect C# API signatures without launching the game, use a `MetadataLoadContext` reflection
dumper (a console project in the scratchpad worked well): load `Assembly-CSharp.dll` with
core-assembly name `"mscorlib"` and print members of the relevant types. `ilspycmd` did not run
under the installed .NET runtime.

## EAC

As a server-side-only DLL with `SkipWithAntiCheat=true`, EAC can **stay enabled** on a dedicated
server (the flag makes EAC *clients* skip the DLL; the server still loads server-side mods). Do not
document this as "EAC must be off".
